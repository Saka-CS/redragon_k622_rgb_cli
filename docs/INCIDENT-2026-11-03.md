# Incident record — K622 `09 d0` write, 2026-11-03

**Severity:** unrecoverable at the application level. The test keyboard stopped
enumerating on USB after an unvalidated write sweep into persistent `09 d0`
state.
**Status:** recorded 2026-11-04. The experimental write path has been removed;
the remaining `09 d0` writer is hardened. Hardware recovery is a separate
track (ISP/programmer or RMA), not part of this repository's test plan.

This document records what happened, why it should have stopped earlier, and
which rules now prevent a repeat. The policy is in
[SAFETY.md](SAFETY.md).

## 1. Environment

| Item | Value |
|---|---|
| Board | Redragon K622 Horus TKL RGB, wired USB |
| USB ID | `258a:0049` (BY Tech / Sinowealth) |
| MCU | Sinowealth SH68F90A / BYK916, 64 KB flash |
| Control interface | IF1, usage page `0xFF00`, usage `0x01`, `/dev/hidrawN` |
| IF1 descriptor | 227 bytes, sha256 `32771137a995e90b6fa9d210761c23ce61e60a21accd033b86f484f198a5061c` |
| Host | Linux, hidraw, udev `uaccess` rule installed |
| Python | 3.14.8 |
| Code under test | the tree that still contained the experimental `set --game-flag` path |
| Removal commit | `96d187d` — "Remove experimental game-flag feature" |
| Documentation baseline | `8dbed9d` — "Updated Docs"; record written on `harden-d0-restore` at `feb5f3a` |

The incident predates the hardening branch. The failing code was the opt-in
`set --game-flag` experiment, which could change one caller-supplied byte of
the 1024-byte `09 d0` payload and send the whole table. It was never part of
normal per-key lighting: `set`, `group apply`, `mode set`, `off`,
`color set` and `profile load` do not write `09 d0`.

The board was used with isolated XDG/state directories and a full
config/palette/custom-frame backup before the first experimental write. That
backup was real and readable, but it could not save the board once the firmware
stopped running (section 7).

## 2. What was being tested

The hypothesis was that one byte in the 1024-byte `09 d0` table selected a
"game mode" or a key-group overlay. The byte offset was unknown. Instead of
stopping when the evidence ran out, the experiment widened into a sweep:

- roughly **330** `09 d0` offset/value combinations;
- offsets `0–5` (the zero header at the start of the table);
- offsets at the observed plane boundaries, including `0x180` (384) and
  `0x310` (784);
- values `0x00`, `0x01` and `0xFF`, including writing `0xFF` into a zero byte;
- d0-only writes and `09 cc` + `09 d0` sequences;
- a full 1024-byte persistent table written for every combination;
- roughly **0.12 s** between writes, about 8 writes per second.

None of these offsets is a documented protocol field. The table is
persistent firmware state, not a scratch buffer. The sweep was not a
compatibility test; it was a high-rate fuzz of an undocumented persistent
region.

## 3. Timeline

1. **Prior validation.** Offsets `6`, `384` and `784` were tried with values
   `0x00`, `0x01` and `0xFF`. No visible lighting change was observed, and a
   restore from the backup worked. This was read as "the byte is harmless",
   which was the first wrong inference: "no visible effect" is not
   "safe to write persistently".
2. **Track B — two `EPIPE` stalls.** Two simple `09 d0` writes stalled with
   `EPIPE`. The tool retried reads and the run appeared to continue. This was
   the clearest stop signal in the whole sequence. A transport error on a
   write path means the device or firmware is already unhappy; retrying reads
   until something passes hides that. Hardware work should have stopped at the
   first `EPIPE`.
3. **C1 — `09 cc` comparison.** Five different `09 cc` frames were sent.
   `09 d0` did not change. This showed that d0 is not a shadow of cc. It did
   not justify writing d0.
4. **C2a — broad sweep.** About 330 `09 d0` writes at roughly 0.12 s each,
   covering offsets `0–5`, plane boundaries and `0xFF` values. This is the
   step that killed the board.
5. **Interruption.** The process was interrupted mid-write. The exact
   interruption trigger was not recorded. The important fact is that the
   `finally` restore did not run: the last modified payload stayed in
   persistent state.
6. **Loss of enumeration.** The keyboard went dark and disappeared from USB.
   It no longer appeared as `258a:0049` in `lsusb`.
7. **Replug test.** The board was replugged on two different laptops. Neither
   restored enumeration, and there were no LEDs at any point.

## 4. Why the earlier `EPIPE` stalls mattered

`EPIPE` is not a benign read timeout. On this device it means a feature
transfer ended without the expected response from the firmware. Two of them
occurred before the sweep. The correct action after the first one was:

- stop all hardware work;
- leave the device idle;
- record the exact command, report and payload;
- diagnose the transport or firmware state before sending another write.

Instead the tool retried reads and the experiment continued. That converted a
recoverable stall into a sustained write campaign against a firmware endpoint
that had already failed. The incident is therefore not only a bad-offset
story; it is a failure to honour a stop condition.

## 5. Why the rollback did not run

The experiment's restore lived in a `finally` block. That only helps if the
process reaches it. An interrupt during a blocking HID write can bypass the
restore, and a failed write can leave the device unable to accept the restore
at all. There was also no independent watchdog, no one-write limit and no
operator confirmation between combinations.

A rollback path that depends on the same process, the same USB endpoint and
the same firmware is not a safety mechanism. It is a best-effort cleanup.

## 6. Resulting state

- No LEDs on any key or logo zone.
- No USB enumeration: `258a:0049` absent from `lsusb`.
- No response to replug on two laptops.
- The last written d0 payload remained in persistent state; the exact failing
  byte is unknown.
- The app-level backup was intact but unusable (section 7).

## 7. Why app-level backups cannot fix this

`k622rgb config restore --custom` is an application-level restore. To work it
must:

1. find the device by VID/PID;
2. open the IF1 hidraw node;
3. talk to the running firmware over feature reports `0x05`/`0x06`;
4. write the palette, config, custom frame 1 and custom frame 2.

A board that does not enumerate fails at step 1. There is no hidraw node, no
descriptor to verify and no mailbox to answer. A verified backup is data, not
a recovery tool. The same is true of the official Windows application: it
needs a device the operating system can see.

This is why the incident is unrecoverable "in software". Recovery must happen
below the application: ISP/programmer access to the MCU flash, or RMA.

## 8. Recovery options

### Attempted

- Replug on the original machine and on a second laptop.
- Different USB-C cable, port and connector orientation.
- `Fn+Esc` reset.
- `lsusb` checks on both machines.

None restored enumeration or LEDs.

### Not attempted during the incident

- Sinowealth ISP / Arduino recovery (`sinowealth-fw-disabler` + `sinowisp`).
- The official K622 updater (`Update_KB_K622RGB.exe`) with matching `.hex`.
- Redragon RMA/support.

These require either physical access to the MCU or a board that still
enumerates in the updater's expected mode. They were not part of the
experiment plan, which is itself a finding: a recovery path must be identified
**before** the first write, not after the board disappears.

### Correct future path

1. Try a different USB-C data cable, port and both orientations.
2. `Fn+Esc` reset.
3. App-level restore only if the device enumerates, using a verified backup:
   `./bin/k622rgb config restore --custom <backup> --yes`.
4. Sinowealth ISP / Arduino:
   `gashtaan/sinowealth-fw-disabler` (Arduino D2/D3 to USB D+/D−, D4 to +5 V),
   then `sinowisp` (`cargo install --locked sinowisp`).
5. Official K622 updater `Update_KB_K622RGB.exe` plus the matching `.hex`.
   The layout (US/UK/ABNT2) must match the board.
6. Redragon RMA/support: `support@redragonshop.com`.

**Do not flash K621 firmware onto a K622.** It is model-specific and is
reported to break keys and LEDs. It is not a recovery path.

## 9. Lessons

1. **Never write unknown or reserved persistent bytes.** "No visible effect"
   is not evidence of safety. A persistent table can affect enumeration,
   key scanning or firmware state without changing an LED.
2. **Stop on the first `EPIPE`.** Do not retry reads until the run looks
   healthy, and do not send another write. Record the failure and stop.
3. **A successful flash is not a compatibility check.** Writing the same
   bytes back, or restoring a backup once, does not prove that adjacent
   states are safe. The board accepted every write until it did not.
4. **A verified backup and a recovery path are prerequisites.** Before any
   persistent write, know where the backup is, verify its hashes, confirm it
   was made from this descriptor, and know how the MCU will be recovered if
   the board stops enumerating.
5. **Prefer a sacrificial device.** Experiments on undocumented persistent
   state belong on hardware that can be lost, not on the only board.
6. **One process, one write.** Bulk sweeps multiply exposure and remove the
   operator's chance to stop. The hardening now permits one forward `09 d0`
   write per process plus at most one rollback write.

The current policy is in [SAFETY.md](SAFETY.md). The removed experiment must
not be re-added in any form: no `--game-flag`, no generic `debug d0`, no
offset/value option, no region or `0xFF` sweep.
